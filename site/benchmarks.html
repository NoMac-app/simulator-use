The most token-efficient iOS Simulator tool for agents.

Eight tools signed in to the same app on the same iPhone 17 Pro Simulator, on one Mac, each through its own MCP server (AXe, which has none, through its command line). simulator-use read 194 tokens per sign-in: 3.4x fewer than the next tool, 66x fewer than Xcode MCP and 569x fewer than AXe. It also signed in fastest: 3.50 s step by step and 2.87 s batched. Every call was timed and saved, failures included.

How each tool was driven

Each tool's own calls, chosen from its README, its tool descriptions or the hints in its answers. The code is in bench/tools.

  • simulator-use. Read with ui_look; ui_act with tap #signIn or fill #email .... Batched: one ui_act with the three steps.
  • AXe. No MCP server, so one axe process per step: describe-ui, tap --id, and tap --id then type. Batched: one axe batch with the five steps, as in its help. It ran twice: with the Simulator headless, like every tool, and again with Device Hub open, since its README says "Xcode 27 simulator automation uses Device Hub".
  • MobileBuildMCP. Run twice, like AXe, which it taps and reads through: headless, and with Device Hub open. Its ui-automation workflow turned on. snapshot_ui, then tap and type_text by elementRef, and snapshot_ui again after each type_text (its descriptions say to refresh after layout changes, and the keyboard is one). Its read lists only tap targets, so the last step checks "Welcome" with its wait_for_ui textContains, as its tips say. No batched run: its batch takes taps, not typing.
  • mobile-mcp. mobile_list_elements_on_screen, then mobile_click_on_screen_at_coordinates by @ref, and a click then mobile_type_keys. Batched: mobile_batch_commands. Its first read starts its on-device agent, which left the Home Screen in front; the setup starts the agent and the app is then started again, as before every step.
  • agent-device. Setup: open with foreground: true, as its instructions say. snapshot with interactiveOnly, press and fill by id="..." selector with settle: true. Batched: its batch.
  • Argent. Setup: the Simulator booted by Argent's boot-device (its first describe said it needs that for its accessibility settings), then launch-app. describe, then gesture-tap at the centre of the element's frame, and a tap then keyboard. Batched: run-sequence.
  • Maestro MCP. inspect_screen, then run with inline YAML: tapOn by id, and tapOn then inputText in one call. Batched: one run with every step.
  • Xcode MCP. Headless (sudo xcrun mcp-server enable). DeviceInteractionStartSession, then DeviceInteractionSynthesize: with no command to read (the agent opens the hierarchy file it names), t x y at the element's hitPoint, and t x y sender keyboard kbd ... to tap a field and type, from Xcode's own device-interaction skill. No batched run: typing must come last in a command.

Method

Every run was on one Mac, one tool at a time, with every other tool's processes ended and the Simulator shut down and booted again before it. AXe and MobileBuildMCP ran a second time with Device Hub open. The harness speaks MCP over stdio to the tool's own server, as an agent's client does, and times each call from the request sent to the answer received (AXe has no MCP server, so its command ran once per step, timed from start to exit). Every tool used its own read, its own way to tap and type (by id where it has one, at coordinates where that is its way), its own settle and verify options, and the setup its docs or its own hints ask for. A tap or a sign-in counts only when the app's own log shows it, a check that uses no accessibility; a step that failed is reported, never retried.

Tokens are what the agent reads back: the answer's text as characters / 4 (no Anthropic API key was set for this run; the harness counts with Anthropic's token counting API when one is), an image as width * height / 750, and for Xcode the hierarchy file its answer points to, which its own skill says to read after every interaction.
